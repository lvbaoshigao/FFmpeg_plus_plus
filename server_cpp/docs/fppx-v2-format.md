## 0. 两项核心约束

| # | 约束 | 含义 |
|---|---|---|
| 1 | **旧版格式冻结** | `fppx_legacy.*` 不作修改。旧版结构不包含索引或加密的扩展位置（定长头 9B + descLen + dataLen + gzip(JSON)，无模块系统）。GUI 选中「旧版」时，索引与加密功能均不可用，协议层**拒绝接收**这两个参数。 |
| 2 | **v2 文件头 6 字节不动** | 魔数 4B + `0xFF` + 模式字节，逐字节保持。不新增特征位，不引入版本号。 |

**通用规则（本次设计的核心）**：
> 凡是**大小不固定**的容器，均在其**开头**放置索引，记录索引自身及后续各元素的**绝对偏移**与**大小**。

该规则适用于顶层容器及模块内部。索引属于**写入时计算、仅在保存时写入文件**的派生数据；编辑过程中不维护或重新计算。

## 1. 总体布局

```
┌────────────────────────────────────────────────────────────────┐
│ 文件头 6B │ 索引模块 0x00 │ 是否加密 0x02 │ 模块序列 … │ 0xFF  │
└────────────────────────────────────────────────────────────────┘
   偏移 0        偏移 6          紧接索引后      0x01 0x03 [0x05] 0x04
```

固定顺序（未加密）：

```
文件头 → 0x00 索引 → 0x01 介绍 → 0x02 是否加密 → 0x03 数据 → 0x04 CRC32 → 0xFF 结尾
```

加密时在 `0x03` 与 `0x04` 之间插入 `0x05` 认证标签：

```
文件头 → 0x00 索引 → 0x01 介绍 → 0x02 是否加密 → 0x03 密文 → 0x05 MAC → 0x04 CRC32 → 0xFF 结尾
```

**索引一律以明文保存**，以便在解密前定位 `0x03`；`0x02` 同样以明文保存，以便在解密前判断是否需要解密。

## 2. 文件头（不动）

| 偏移 | 长度 | 字段 | 取值 |
|---|---|---|---|
| 0 | 4B | 魔数 | `46 50 50 58` = "FPPX" |
| 4 | 1B | 重构版标记 | `0xFF` |
| 5 | 1B | 模式 | `0x01` 节点编辑器 / `0x02` 快速模式 |

格式判别仅依据第 4 字节（旧版该字节为 `configMajor = 0x01`），因此两种格式互斥。

---

## 3. 模块帧

偏移 6 起，每个模块自描述：

```
[1B] 模块 ID
[4B] 载荷字节数 N（大端）
[NB] 载荷
```

模块 ID 分配：

| ID | 名称 | 说明 |
|---|---|---|
| `0x00` | **索引** | 本次新增，恒为第一个模块 |
| `0x01` | 介绍 | UTF-8 文本，可空 |
| `0x02` | 是否加密 | 未加密时恒为 1B `0x00`；加密时为变长记录（见 §6.2） |
| `0x03` | 数据 | 节点图 / 快速参数；**加密时本模块载荷整体为密文** |
| `0x04` | CRC32 | 4B 大端，覆盖 `[0, 本模块 ID 字节偏移)` |
| `0x05` | 认证标签 | 仅加密时存在，MAC 值 |
| `0xFF` | 结尾 | 载荷 0 字节，其后不得有数据 |

未知 ID 的既有处理语义保持不变：**warning + `skip(sz)`**，以维持向前兼容性。

## 4. 索引模块 `0x00`

### 4.1 载荷结构

```
偏移  长度  字段
0     1    版本        = 0x01
1     1    步长        = 9（单条目字节数；将来加字段时旧读者可整体跳过）
2     2    保留        = 0
4     4    条目数 K    大端
8     K×9  条目区
```

单条目：

```
[1B] 元素 ID     模块 ID（内层索引时为内层元素类型，见 §5）
[4B] 绝对偏移     从文件首字节起算
[4B] 大小        含该元素 5B 头（内层元素无头，则为元素自身字节数）
```

载荷长度 = `8 + 9K`；模块总长 = `13 + 9K`。

### 4.2 关键约定

- **第 0 条记录索引自身**：`id=0x00, offset=6, size=13+9K`。据此，条目覆盖“文件头之后的全部内容，直至文件末尾”，相关校验条件得以闭合。
- **条目按写入顺序排列**，且偏移严格递增。末条必须为 `0xFF` 结尾模块。
- **K 在写入索引前即可确定**（本次待写入的模块数已确定），因此**无需回填**。
- **写入时机：软件实时计算，但仅在用户点击「保存」时写入一次**。编辑过程中不重新计算偏移，也不写入文件。

### 4.3 索引校验（读取侧）

检查分为两组，**两组失败时的处理方式不同**：

**A 组：结构自洽性（仅检查索引自身）** —— 任一条件不成立即判为「结构非法」，并执行 `warning + 回退线性扫描`（见 4.4）：

1. 载荷长度 ≥ 8
2. `版本 == 0x01` 且 `步长 == 9`
3. `8 + 9K == 载荷长度`
4. `条目[0].id == 0x00 && 条目[0].offset == 6 && 条目[0].size == 13 + 9K`
5. 偏移严格递增（等价于不重叠）：`条目[i].offset >= 条目[i-1].offset + 条目[i-1].size`
   且 `条目[i].size != 0`；判断用 **64 位**求和，避免 `offset+size` 在 32 位回绕
6. `条目[K-1].offset + 条目[K-1].size == 文件总长`，且末条 `id == 0xFF`

**B 组：与文件实际内容一致性** —— 索引结构合法但与文件内容不一致时，**直接报错**（见 4.4）：

7. 每个条目的 `offset` 处确实是该 `id`（`bytes[offset] == 条目.id`）
8. 该处模块的 `4B 载荷长度 + 5B 模块头 == 条目.size`
9. `条目.offset + 条目.size <= 文件总长`，且 `条目.size >= 5`

> B 组校验失败时不执行回退，原因如下：只有**新文件**带有顶层索引（老 v2 文件满足 `bytes[6] != 0x00`，采用线性扫描）。索引结构自洽但与文件内容矛盾，表明文件可能已损坏或遭到篡改；此时回退可能将损坏内容作为正常数据读取，因此应直接报错。

### 4.4 有无索引的判定与回退

| 条件 | 行为 |
|---|---|
| `bytes[6] == 0x00` | 有索引，按索引随机访问 |
| `bytes[6] != 0x00` | **无索引**（老 v2 文件），回退**线性扫描** |
| 索引存在但**结构非法**（A 组 1–6 条） | **warning + 回退线性扫描**（不直接报错，以兼容旧文件） |
| 索引结构合法但**与实际内容不符**（B 组 7–9 条） | **报错**——索引自洽但与实际内容不符，表明文件已损坏或遭到篡改 |
| 索引合法、CRC 通过，仍与解析结果不符 | **报错**——CRC 校验通过但解析结果仍不一致，说明生成端存在缺陷 |

> 判定依据明确：现行导出始终以模块 `0x01` 开头（`fppx2.cpp:634`），因此 `bytes[6]` 不会是 `0x00`。

## 5. 内层索引（`0x03` 载荷内部）

同一套规则向下递归应用。当前 `0x03` 载荷由 `[4B 节点数 N]` 及各自带 4B 长度的记录组成；若要定位第 i 个节点，必须从头依次遍历全部前置记录。加入内层索引后，可直接定位目标节点。

### 5.1 `0x01` 节点编辑器模式

```
[内层索引][节点记录区][逻辑块区]
  ├ 内层索引：同 §4.1 结构；第 0 条同样是索引自身（`id=0x00`、`size=8+9K`，
  │           注意内层索引**没有 5B 模块头**，故自条目大小为 `8+9K` 而非 `13+9K`）
  ├ 节点记录区：N 条节点记录（结构不变，仍以 `[4B N]` 开头）
  └ 逻辑块区：  M 条逻辑块（结构不变，仍以 `[4B M]` 开头）
```
K = 3（索引自身 + 节点记录区 + 逻辑块区），故内层索引固定 35 字节。

### 5.2 `0x02` 快速模式

```
[内层索引][参数项区]
```
K = 2（索引自身 + 参数项区），故内层索引固定 26 字节。

> **读侧宽容（实现口径）**：内层索引是**加速层**，不是必需层。读端只按
> 「前 4 字节恒为 `01 09 00 00`」判断有无，并据此跳过 `8+9K` 字节；
> 结构非法时按“无内层索引”处理（`innerIndexSkip()` 返回 0），**不报错**。
> 依据：老 v2 载荷此处是 `[4B 节点数]`，而节点数 ≥ `0x01090000` 在现实中不可能，
> 因此该判定不存在歧义，可同时读取“无内层索引的老载荷”与“有内层索引的新载荷”。

### 5.3 内层元素 ID（独立命名空间，不与模块 ID 共用）

| ID | 名称 |
|---|---|
| `0x01` | 节点记录区 |
| `0x02` | 逻辑块区 |
| `0x03` | 参数项区 |

### 5.4 偏移口径

**一律绝对偏移**，内外层同一套规则。

> 已知并接受的代价：内层偏移位于密文中，具有位置敏感性；载荷位置改变后，内层索引将失效。当前格式不受影响，因为载荷不会移动。若未来支持分块重排，则需改为“相对载荷起点”偏移，并升级内层索引版本号。

## 6. 加密设计

### 6.1 边界：哪些明文、哪些密文

| | 内容 |
|---|---|
| **明文** | 文件头 6B、**索引模块 0x00 整体**（含所有 ID/偏移/大小）、模块 `0x01` 介绍全文、模块 `0x02` 加密信息（algo/kdf/iters/salt/iv）、模块 `0x05` MAC 值、模块 `0x04` CRC32、`0xFF` 结尾 |
| **密文** | **仅模块 `0x03` 的载荷**（节点图 或 快速参数），含其**内层索引** |

三条必须向用户明示的代价：

1. **介绍文本以明文保存** —— 无需输入口令即可读取。UI 需提示“勿在介绍中写敏感信息”。
2. **密文长度暴露明文量级** —— CBC 填充后长度 = `ceil((D+1)/16) × 16`。可选缓解见 §6.7。
3. **未知节点类型的检测整体后移一步** —— 当前 `parseNodeGraph` 在开始解析时即查询注册表（`fppx2.cpp:267`）；加密后必须先解密，"是否含未知类型"的检查以及"强制导入确认框"的触发时机都挪到解密之后。

### 6.2 模块 `0x02` 载荷（变长）

必须**向后兼容既有 1 字节形态**（当前已生成的 v2 文件均为 `长度==1 且值==0x00`）。当前代码 `sz != 1` 直接报错（`fppx2.cpp:839`），要放宽为「1 或 ≥13」。

```
未加密（旧形态，必须继续可读）：
  长度 = 1，值 = 0x00

加密：
偏移  长度  字段
0     1    algo       0x01 = AES-128-CBC / 0x02 = AES-256-CBC
                       0x11 / 0x12 预留 GCM（本版不实现）
1     1    kdf        0x01 = PBKDF2-HMAC-SHA256
2     4    iters      迭代次数（大端）
6     1    macAlgo    0x01 = HMAC-SHA256 / 0x00 = 无
7     2    saltLen    大端，建议 16
9     2    ivLen      大端，CBC = 16，GCM = 12
11    2    macLen     0 或 32（GCM 时 16）
13    Ls   salt
13+Ls Li   iv
```

### 6.3 算法族取值

| algo | 含义 | 本版 |
|---|---|---|
| `0x00` | 不加密 | 现有行为 |
| `0x01` | AES-128-CBC + PKCS#7 | 支持 |
| `0x02` | AES-256-CBC + PKCS#7 | 支持，**默认** |
| `0x11` / `0x12` | AES-128 / 256-GCM | **预留**（算法字节先占住，将来换实现不动格式） |
| ECB / AES-192 | — | 永不支持（前者不安全，后者无收益） |

未知 `algo` 沿用现有处理语义：**明确报错并拒绝**，不静默忽略（`fppx2.cpp:907-913` 已有此行为）。

### 6.4 模块 `0x05` 认证标签

- 位于 `0x03` 之后、`0x04` 之前 —— **无需回填、长度不变**，因此顺序符合要求。
- 载荷 = MAC 值（HMAC-SHA256 为 32B）。

### 6.5 MAC 覆盖范围（本次设计的关键点）

**MAC 覆盖 `[0, 0x05 模块 ID 字节偏移)`**，即：文件头 + 索引 + `0x01` + `0x02` + 密文。

> MAC 不应仅覆盖密文，因为**索引本身也是需要认证的元数据**。若 MAC 仅覆盖密文，攻击者可以改写索引条目（例如将某个模块的偏移指向其他位置），再重新计算 CRC32（CRC 不是 MAC，可被重新计算），从而使读取端解析错误位置。**索引必须纳入 MAC 覆盖范围。**

无循环依赖：MAC 计算时所需的一切（含索引里 `0x05`、`0x04` 自身的偏移与大小）都在计算前已确定。

实现方式与现有 CRC 的处理方式一致：在写入 `0x05` 之前，对已累积的 `w.buf` 整体计算 HMAC：

```cpp
uint8_t mac[32];
hmacSha256(macKey, w.buf.data(), w.buf.size(), mac);
w.u8(FPPX2_MODULE_MAC);
w.u32(32);
w.raw(mac, 32);
```

### 6.6 密钥派生

- **PBKDF2-HMAC-SHA256**，salt **16B 随机**（写入时生成并存入 `0x02`）。
- 迭代次数：桌面 **200 000**，移动端 **100 000**（写端决定并存入 `0x02`，读端照用）。
- **读端上限 `FPPX2_PBKDF2_ITERS_MAX = 1 000 000`**：`0x02` 里的 iters 来自文件（不可信），
  超限即判为非法，并**在派生之前**返回错误，避免执行不必要的高耗时派生计算。记录的本机测量结果（MSVC `/O2`）：
  10 万 ≈ 0.29s、20 万 ≈ 0.55s、100 万 ≈ 2.6s、500 万 ≈ **14.1s**。GUI 侧
  `fppx_import` / `fppx2_export` 的请求超时为 **30s**（`backend_client.dart`），
  故上限取 100 万（≈11× 余量）：给自定义文件留足余地，又不至于被一个坏文件拖到超时。
- 输出长度：AES-128 → `16B 密钥 + 32B MAC 密钥 = 48B`；AES-256 → `32 + 32 = 64B`。

### 6.7 填充与长度隐藏（可选项）

默认仅执行 PKCS#7 最小填充。若需隐藏明文长度量级，可“填充到 1KB 边界”，此时：

- 索引与 `0x03` 长度字段记录的是**填充后（密文）长度**；
- **真实明文长度必须写在密文内部**（建议密文首个 4B），解密后读；
- 索引**仅记录落盘尺寸**，不额外记录明文长度，以免抵消填充的长度隐藏效果。

### 6.8 口令错误 vs 文件损坏（已决定：不做 verifier）

**不区分口令错误与文件损坏。** 采用 MAC 优先验证，验证失败时返回统一错误文案：

> 口令错误，或文件已损坏 / 被篡改

理由：文件本身已支持离线口令尝试（MAC 可作为现成的 oracle）。增加 8B verifier 只能使错误说明更精确，却需要在 `0x02` 中增加字段，并增加一个攻击者可直接查询的 KCV。采用统一文案可避免误导用户，也不会额外削弱安全性。

**保留未来扩展能力**：`0x02` 载荷为变长结构，`saltLen` / `ivLen` / `macLen` 均为显式长度。未来如需增加 verifier，可将其追加在 `salt + iv` 之后；读取端将“尾部多出的字节”作为未知扩展，按**忽略 + warning** 处理，不报错。本版不写入、不读取，也不校验该字段。

### 6.9 导入交互流程（已定）

```
导入加密文件
  |
  +-- 读 0x02，algo != 0x00 → 需要口令
  |
GUI 弹出「输入口令」对话框（文件路径已知，无需重选文件）
  |
  +-- 用户输入 → 提交；或取消 → 中止导入，提示「已取消」（不按错误处理）
  |
C++: PBKDF2 派生 → 重算 MAC 覆盖 [0, 0x05 起始) → 常数时间比对
  |
  +-- 失败 → 返回「口令错误，或文件已损坏 / 被篡改」
  |          → 对话框保持打开，允许直接重试
  |
  +-- 成功 → 解密 0x03 → 校验 PKCS#7 填充 → 解析 → 打开
```

约束：

- **口令不写入磁盘、日志或审计记录，也不出现在错误信息中**；使用后立即清零内存。
- 导入失败**不改变原文件**（导入路径为只读，不会写入原文件）。
- **空口令一律拒绝**（导出、导入两侧均拒绝），避免用户误以为文件已加密。
- 导出侧口令需**二次确认输入** —— 口令一旦输入错误，文件可能无法打开；因此须在写盘前完成确认。
- 用户取消口令框 → 中止导入并提示“已取消”，不作为错误弹窗处理。

## 7. 写路径流程（`fppx2Export`）

当前流程为“边序列化边写入模块 + 回填长度”；索引要求分为**两趟**处理：

1. **收集载荷**：把 `0x01` / `0x02` / `0x03`（含内层索引）/ `0x05` / `0x04` / `0xFF` 的载荷全部先在内存里序列化好。
   （当前代码已将节点图预先序列化到 `ByteWriter`，见 `fppx2.cpp:700-704`，因此所需改动较少。）
2. **算偏移**：`索引长度 = 13 + 9K` → 依次推出每个模块的绝对偏移与大小。
3. **加密**（若启用）：先校验口令非空（GUI 侧已二次确认）→ 生成 salt/IV → PBKDF2 派生 → 加密 `0x03` 载荷 → 得到密文。
4. **写盘**：文件头 → 索引模块 → `0x01` → `0x02` → `0x03` → 对 `w.buf` 整体 HMAC → 写 `0x05` → 算 CRC → 写 `0x04` → `0xFF`。
5. **写后自校验（必须修改）**：现有代码为 `Fppx2Result verify = fppx2Import(path, false);`（`fppx2.cpp:752`），调用时**未传入口令**。因此，加密文件重读时必然失败，`verify.success == false` 会触发 `std::filesystem::remove`，导致刚写入的文件被删除。自校验调用必须传入本次导出使用的口令。
   传入口令后，自校验也会覆盖加密路径：若写入端与读取端的密钥派生不一致，文件将被删除并返回错误，从而避免留下无法打开的文件。

## 8. 读路径流程（`fppx2Import`）

```
校验文件头 → 校验模式
  ↓
bytes[6] == 0x00 ? 解析索引 + 按 §4.3 校验 : 线性扫描（老文件回退）
  ↓
读 0x02 → algo == 0x00 ? 跳过 : 读 salt/iters/iv
  ↓
（加密时）PBKDF2 派生 → 重算 MAC 覆盖 [0, mac_offset) → 常数时间比对
  ↓  MAC 失败 → 返回「口令错误，或文件已损坏 / 被篡改」；口令框保持打开可重试
解密 0x03 载荷 → 校验 PKCS#7 填充
  ↓
CRC32 校验（口径不变，仍覆盖 [0, crc 起始)，包含索引与 MAC）
  ↓
parseNodeGraph / parseQuickItems（未知节点类型检查在此，晚于解密）
```

**先验证 MAC，再执行解密**（encrypt-then-MAC 的标准顺序）：MAC 覆盖密文，可在解密前完成验证。

## 9. 体积计算

未加密（`K = 6`：索引自身 + `0x01/0x02/0x03/0x04/0xFF`）：

```
索引模块 = 13 + 9×6 = 67
文件总长 = 103 + L + D      （L = 介绍字节数，D = 数据载荷字节数）
```

加密（`K = 7`，多一个 `0x05`）：

```
索引模块 = 13 + 9×7 = 76
加密增量 ≈ 90 + 1~16 字节
       = 索引多一条 9 + 0x02 扩展载荷 44 + MAC 模块 37 + PKCS#7 填充
```

> **Dart 端 `_fppxSizeBytes`（`pipeline_editor_page.dart:7677`）的 `+48` 常量必须同步调整**，否则底栏显示的 `≈ x KB` 会偏小；加密时还需按 `ceil((D+1)/16)×16` 估算 `D`，不可直接使用明文字节数。

**若干实现细节（规范未明示，现予补充）**

1. **两趟写入的计算依据**：索引长度仅取决于模块个数 K（未加密 6 / 加密 7），与载荷大小无关，
   因此可在序列化载荷**之前**计算 `plaintextStart` —— 内层索引需要写入绝对偏移，
   因而必须预先确定其位置。
2. **内层索引在加密下的语义**：内层条目记的是「明文坐标」下的绝对偏移
   （= `0x03` 模块载荷起始 + 载荷内相对偏移）。CBC 加密后密文仍落在同一起始位置，
   故该偏移在加密前后都成立；密文尾部多出的填充字节不属于任何内层区域。
3. **校验顺序**：`读 0x02 → 派生 → 验 MAC（覆盖 [0, 0x05 起始)）→ 解密 → 校验 PKCS#7 → CRC32 → 解析`。
   MAC 失败与解密失败返回**同一句**文案，不区分（§6.8）。
4. **索引合法性校验**：索引存在但结构非法 → `warning + 回退线性扫描`；
   索引合法但条目与实际内容不符（ID 或帧长不一致）→ **报错**（CRC 校验通过但仍不一致，
   说明生成端存在缺陷）。
5. **写入后自校验必须传入口令**（§7 步骤 5）：否则加密文件重读必然失败，
   `verify.success == false` 会触发 `std::filesystem::remove`，导致刚写入的文件被删除。
6. **异常处理的职责划分**：`dll_main.cpp` 已通过 `try/catch` 捕获每条 fppx 命令的异常，
   异常会转成 `success=false` + `服务器异常: ...` 回复，**不会 abort 进程**；
   但该处理路径会将 nlohmann 的原始异常文本传递给 GUI，因此 `fppx2Import` 在解析载荷时
   增加一层 `try/catch`，转换为「配置载荷结构非法（解析中止）」等明确的错误信息。
7. **算法参数先按 int 校验、再收窄**：`encrypt_algo` 若直接 `static_cast<uint8_t>`，
   `0x102` 会被截断为合法的 `0x02`，导致非法值通过校验；现改为先按 int 比较，再进行转换。
